# ADR-004：工具注册与分批交付

## 状态

已接受。

## 背景

用户确认继续扩展工具箱，目标覆盖 URL、UUID、Hash、HTTP、MIME、JWT、Diff、编码、颜色、进制、文本处理、Mock 数据以及多种数据格式转换。若继续以单页硬编码工具的方式扩展，会带来三个问题：

1. 导航和路由难以维护。
2. 状态模型重复膨胀。
3. 测试与验收难以分批推进。

## 决策

1. 建立统一工具注册表，工具定义包含：
   - id
   - 名称
   - 分组
   - 描述
   - 默认状态
   - 参数归一化逻辑
2. v1 先以现有原生 DOM 架构实现注册表，不引入前端框架。
3. 新工具按批次交付：
   - v1.1 高频通用工具
   - v1.2 联调排查工具
   - v1.3 数据格式转换
   - v1.4 高级体验与离线能力
4. 每批交付必须同步：
   - 设计文档
   - roadmap
   - 实现代码
   - 自动化测试
   - 验收记录
5. 每个工具保持独立纯逻辑模块或清晰的纯函数集合，便于 Node 测试复用。
6. 速查类工具不引入后端，数据内置在本地静态资源中。

## 备选方案

### 方案 A：继续在现有单文件中追加

优点：
- 短期改动小。

缺点：
- `core.js` 和 `app.js` 快速膨胀。
- 无法分批验收。
- 后续维护成本高。

### 方案 B：立刻迁移到 React / Vue

优点：
- 组件化和状态管理更成熟。

缺点：
- 与 ADR-002 的无构建、零依赖决策冲突。
- 当前工具以表单和文本转换为主，框架收益不足。

### 方案 C：注册表 + 纯逻辑模块 + 原生 DOM

优点：
- 保持零依赖和静态部署。
- 逻辑可测试。
- 工具可分批接入。
- 为未来框架迁移保留边界。

缺点：
- 需要手写 UI 渲染与状态绑定。
- 复杂交互工具实现成本高于框架方案。

## 后果

### 正面影响

1. 工具数量增加时导航、路由和状态结构可控。
2. 每批功能都有明确验收边界。
3. 核心转换逻辑可长期复用。

### 负面影响

1. 原生 DOM 实现的工作量随工具复杂度上升。
2. 后续如果做复杂树形视图或协同编辑，仍需重新评估框架迁移。

### 重新评估触发条件

1. 工具状态和 DOM 绑定代码明显失控。
2. 需要复杂组件树、拖拽布局或协同编辑。
3. 注册表抽象开始阻碍而不是简化功能实现。
