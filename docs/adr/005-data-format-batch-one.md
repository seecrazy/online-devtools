# ADR-005：v1.3 第一批数据格式工具实现方案

## 状态

已接受。

## 背景

v1.3 规划包含 CSV、YAML、TOML、XML、SQL、Markdown 等格式工具。YAML 与 TOML 的完整语法复杂（锚点、多行字符串、类型强转等），自写解析器质量风险高；引入第三方库则需要在零依赖静态部署约束下评估包体与供应链。

## 决策

1. v1.3 第一批实现 **CSV ↔ JSON、JSON → TypeScript、XML 校验与格式化**，全部使用零依赖纯函数：
   - CSV：自写 RFC 4180 常用子集解析器（引号字段、双引号转义、字段内换行、可配置分隔符）。
   - TypeScript 生成：基于 JSON 值自写类型推断与 interface 生成。
   - XML：自写 tokenizer 做良构性校验与缩进格式化，不引入 DOMParser 依赖，保证 Node 测试可运行。
2. YAML ↔ JSON 与 TOML ↔ JSON 延后到 v1.3 第二批，实现前单独评估：
   - 方案 A：引入经审计的浏览器兼容解析库（懒加载）。
   - 方案 B：自写明确文档化的子集解析器。
3. XML 不做 DTD / XSD 校验，仅保证良构性检查。
4. 输入上限沿用全局 1 MiB 限制。
5. 全部处理保留在浏览器本地，无网络请求。

## 备选方案

### 方案 A：第一批直接引入 js-yaml / xml-js 等库

优点：解析覆盖完整。

缺点：与 ADR-002 零构建零依赖方向冲突；需要引入打包或 CDN 运行时依赖；本批工具并不需要这些依赖即可高质量交付。

### 方案 B：全部自写

优点：保持零依赖、体积小、Node 可测试。

缺点：YAML / TOML 完整语法实现成本高、边界多。

### 方案 C（采纳）：第一批自写 + 第二批单独评估

优点：本批快速交付高质量工具；YAML / TOML 风险隔离，不阻塞其他工具。

缺点：YAML / TOML 交付时间推后。

## 后果

1. CSV / XML / TypeScript 生成逻辑以纯函数形式沉淀在 `core.js`，可被 Node 测试覆盖。
2. XML 校验仅覆盖良构性，用户需要 Schema 校验时需使用其他工具。
3. YAML / TOML 交付时间延后，需在 roadmap 中明确为第二批。
