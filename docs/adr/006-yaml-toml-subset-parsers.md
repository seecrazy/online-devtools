# ADR-006：YAML 与 TOML 自写子集解析器

## 状态

已接受。

## 背景

ADR-005 将 YAML 与 TOML 延后到 v1.3 第二批，并要求实现前在引入第三方库与自写解析器之间做出决策。完整 YAML 规范非常复杂（锚点、别名、多文档、类型强转、块标量变体等）；TOML 规范较收敛但仍包含日期时间与多行字符串等边界。零依赖静态部署（ADR-002）约束下引入第三方库需要打包流程或 CDN 运行时依赖。

## 决策

1. 采用 **自写、明确文档化的子集解析器**，覆盖开发者日常配置文件的高频语法：
   - YAML：嵌套映射、`- ` 序列、常见标量、引号字符串、一层行内集合、`|` / `|-` 块标量、注释。
   - TOML：表、数组表、点号键、基本 / 字面量字符串、整数、浮点数、布尔、数组、行内表。
2. 子集边界在工具页面与设计文档中明示；超出子集的输入报可读错误并定位行号，而不是静默输出错误结果。
3. 不引入 js-yaml、smol-toml 等运行时依赖。
4. 解析逻辑以纯函数沉淀在 `core.js`，Node 测试覆盖。

## 备选方案

### 方案 A：引入 js-yaml / smol-toml

优点：语法覆盖完整，边界行为经过广泛验证。

缺点：与零构建、零依赖决策冲突；需要引入打包或 CDN 依赖；子集场景下的收益不抵依赖成本。

### 方案 B：自写完整 YAML 解析器

优点：无依赖且覆盖全。

缺点：实现成本极高，边界行为难以在自测中穷尽，质量风险大。

### 方案 C（采纳）：自写文档化子集解析器

优点：零依赖；覆盖高频场景；错误行为可控且可测试。

缺点：不支持完整规范；用户遇到超出子集的输入会得到明确报错而非解析成功。

## 后果

1. YAML / TOML 工具面向「粘贴一段常见配置并查看 JSON」的场景，不承诺完整规范兼容。
2. 后续如需完整规范，可在不改变 UI 的前提下替换解析内核。
3. 子集边界需同步写入 README 与工具页说明。
