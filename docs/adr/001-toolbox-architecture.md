# ADR-001：静态前端与本地处理架构

## 状态

已提出，等待确认。

## 背景

Online DevTools 的核心需求是 JSON 解析、Base64 编解码、时间戳转换、正则表达式测试和 Cron 表达式解析。这些工具具有以下特点：

1. 输入通常是短文本或中等规模文本。
2. 用户可能粘贴 Token、接口响应或业务配置，对隐私敏感。
3. 操作高频，但计算复杂度可控。
4. 分享需求集中在“当前输入与参数”，而不是长期存储。
5. 早期“在线代码运行 playground”的方向已根据需求调整为开发者工具箱，v1 不执行用户代码。

## 决策

1. v1 采用纯前端静态 Web 应用。
2. 不引入业务后端，不做服务端数据处理。
3. 所有工具默认在浏览器本地计算。
4. 分享状态使用 URL hash 编码，不落库。
5. 主题等界面偏好可使用 `localStorage`，但默认不保存用户输入。
6. JSON 使用原生解析器，不使用 `eval`。
7. 正则匹配优先放入 Web Worker，避免灾难性回溯阻塞页面。
8. Cron 与时间预览优先使用经过测试的本地解析逻辑或可靠前端库。

## 备选方案

### 方案 A：纯前端静态应用

优点：

- 隐私友好，输入不上传。
- 部署简单，可托管在任何静态资源服务。
- 延迟低，无需后端冷启动。
- 与 URL hash 分享天然契合。

缺点：

- 处理超大文件能力有限。
- 需要自行处理浏览器兼容性。
- 某些复杂解析能力实现成本较高。

### 方案 B：服务端 API 处理

优点：

- 便于处理超大文本。
- 便于统一使用特定解析引擎。
- 便于审计和限流。

缺点：

- 输入必须上传，隐私风险高。
- 增加部署、运维和安全成本。
- 延迟和可用性依赖后端。

### 方案 C：混合架构

优点：

- 常用操作本地完成。
- 特殊能力可由后端补充。

缺点：

- 架构复杂度更高。
- 隐私边界不清晰。
- v1 收益不明显。

## 后果

### 正面影响

1. v1 可以快速开发和部署。
2. 用户数据不出浏览器，隐私边界清晰。
3. 无需账号和数据库即可提供完整功能。
4. 运维成本低。

### 负面影响

1. 超大文件处理能力受限。
2. 需要为 Worker、输入截断和计算超时做额外设计。
3. 不同浏览器正则行为需要明确提示。

### 后续触发条件

当满足以下任一条件时，重新评估混合架构或服务端 API：

1. 需要处理明显超出浏览器能力的大文件。
2. 需要跨浏览器、跨语言保持完全一致的正则或 Cron 语义。
3. 需要引入用户账号与云端保存。
4. 需要提供团队协作能力。
